## 1. 내일 처음 읽을 때: 어디까지 했나?

목표는 **staging·prod의 VM이 교체되거나 재부팅돼도 앱이 자동 실행되고, CD가 새 템플릿으로 롤링 배포할 수 있게 만드는 것**이다. 서비스 간 주소는 내부 LB·사설 DNS로 고정하고, Terraform state를 팀이 공유하도록 GCS backend 설정을 추가했다.

| 항목 | 마지막 확인 상태 | 근거와 다음 확인 |
| --- | --- | --- |
| IaC·앱 자동 부팅 | 코드 구현 확인 | 아래 코드 대응표·로컬 검사 참고 |
| staging | 사용자가 정상 확인 후 중지했다고 보고 | 개별 재부팅·교체·CD 시험 출력은 미수집 |
| prod AI VM 부팅 | 설치·이미지 pull·컨테이너 실행 명령 성공 로그 확인 | HTTP 정상 여부는 별도 |
| prod AI 앱 | 마지막 공유 결과는 DB 인증 실패 | mulo 사용자 인증 실패 후 복구 성공 로그 없음 |
| prod AI 시크릿 | 삭제 후 복구 plan까지 확인 | 2개 추가 계획 이후 apply·버전 등록 성공 미확인 |
| prod frontend env | 빈 파일 오류 확인 | 당시 frontend.env 0바이트, 이후 등록 성공 미확인 |
| 원격 state | 세 환경 backend.tf 추가 | 마지막 이전 결과는 버킷 404, 이전 완료 미확인 |
| 운영 LB·내부 통신·CD | 코드·점검 절차 준비 | 실제 전체 성공 결과는 미수집 |
| chat | 이미지 미지정 | 앱 기동·healthy 검증 대상에서 제외 |

**다음 순서:** state 버킷·이전 상태 확인 → 운영 AI 시크릿 및 DB 설정 복구 → AI 두 VM HTTP 200 확인 → 나머지 앱·내부 통신·LB 확인 → staging에서 재부팅·교체·CD 검증 결과 확보.

“미확인”은 반드시 실패했다는 뜻이 아니라 완료 증거가 없다는 뜻이다. 이미 해결했다면 실제 결과를 8절 기록표에 채운다.

### 5-1. state 버킷 404 해결 — Mac 터미널

backend.tf는 버킷 자체를 생성하지 않는다. GCS backend에는 미리 존재하는 버킷이 필요하다. 잠금을 지원하며 객체 버전 관리가 권장된다. [HashiCorp GCS 문서](https://developer.hashicorp.com/terraform/language/backend/gcs)

먼저 존재 여부를 조회한다.

~~~bash
gcloud storage buckets describe gs://mulo-v2-tfstate-953840519216 --project=project-7b071b48-8637-467a-80d
~~~

여전히 404이고 이름·프로젝트가 맞으면 생성한다. 403이면 권한 문제부터 해결한다.

~~~bash
gcloud storage buckets create gs://mulo-v2-tfstate-953840519216 --project=project-7b071b48-8637-467a-80d --location=asia-northeast3 --uniform-bucket-level-access --public-access-prevention
gcloud storage buckets update gs://mulo-v2-tfstate-953840519216 --project=project-7b071b48-8637-467a-80d --versioning
~~~

최신 로컬 state를 가진 담당자 한 명이 기존 state·백업을 안전하게 보관하고 진행한다. 팀의 동시 Terraform 실행은 중단한다. 대상에 state가 이미 있으면 최신본 확인 없이 덮어쓰지 않는다.

~~~bash
cd /Users/lukas.lee/Desktop/mulo-v2-terraform/environments/prod
# ADC 로그인이 필요할 때만 실행
gcloud auth application-default login
terraform init -migrate-state
terraform state list
gcloud storage ls gs://mulo-v2-tfstate-953840519216/prod/default.tfstate
~~~

성공 기준: init 성공, 기존 리소스 주소 유지, GCS 객체 존재. 버킷은 한 번만 만들고 dev·staging은 해당 폴더에서 각각 이전한다. 기본 workspace 경로는 dev/default.tfstate, staging/default.tfstate, prod/default.tfstate다.

최초 이전 후 팀원은 해당 환경에서 `terraform init -reconfigure`로 연결한다. 오래된 팀원 로컬 state를 다시 업로드하지 않는다. Git에는 코드·backend 설정·provider lock 파일·문서를 공유한다. state·백업·plan·실제 env는 올리지 않는다. 버킷 권한과 자세한 절차는 [STATE.md](../environments/STATE.md)를 따른다.

### 5-2. 운영 AI 시크릿 복구 — Mac 터미널

삭제되어 없다면 backend 초기화·state 확인 후 복구 plan을 새로 만든다. state 이전 전에 저장한 tfplan-prod-secrets를 그대로 재사용하지 않는다.

~~~bash
cd /Users/lukas.lee/Desktop/mulo-v2-terraform/environments/prod
terraform plan -target=module.mulo.google_secret_manager_secret.app_env -target=module.mulo.google_secret_manager_secret_iam_member.vm_env_reader -out=tfplan-prod-secrets-recovery
# 의도한 시크릿·IAM 복구인지 검토한 뒤 실행
terraform apply tfplan-prod-secrets-recovery
~~~

이 target은 서비스별 시크릿·IAM 묶음에 해당한다. 새 계획도 반드시 2개 추가인 것은 아니다. 예외적인 복구 후 전체 plan으로 나머지 차이를 확인한다. **plan 저장만으로 실제 시크릿이 만들어지지 않는다.**

Desktop의 ai.env에서 운영 DB 대상·사용자·비밀번호를 맞춘다. DATABASE_URL에 비밀번호가 포함되면 예약 문자의 URL 인코딩이 필요할 수 있다. 인증 실패 로그만으로 어떤 값이 틀렸는지는 확정할 수 없다. 앱에 필요한 전체 env를 유지하며 해당 설정을 수정한다.

~~~bash
# 내용 대신 파일 존재·빈 파일 여부만 확인
test -s "$HOME/Desktop/ai.env" && echo "ai.env 파일 존재, 0바이트 아님"

# 위 검사 성공 및 설정값 검토 후 등록
gcloud secrets versions add mulo-v2-ai-env --project=project-7b071b48-8637-467a-80d --data-file="$HOME/Desktop/ai.env"
~~~

성공 기준: 버전 생성 성공 메시지와 ENABLED 버전. 0바이트가 아닌 것만으로 설정의 정확성까지 확인되지는 않는다.

frontend도 파일명 frontend.env·파일 크기를 확인하고 필요한 런타임 설정을 채워 mulo-v2-frontend-env에 등록한다. 런타임 변수가 전혀 필요 없다면 주석 한 줄 파일은 선택지지만 CI 빌드 설정이 충분한지 먼저 확인한다. 임의의 가짜 설정을 추가하지 않는다. env 값에는 불필요한 따옴표나 마크다운 URL 표시를 넣지 않는다. 등록·복구 확인 후 임시 env 파일은 안전하게 정리한다.

### 5-3. 새 env 반영·AI 복구 확인 — 각 AI VM 안

새 시크릿 버전 등록만으로 실행 중 컨테이너의 env가 바뀌지 않는다. 아래 명령은 해당 VM의 app을 다시 실행한다. AI 두 VM에서 동시에 실행하지 말고 한 대의 복구 결과를 확인한 뒤 다음 대로 진행한다. 정상 운영 이후의 일반 env 변경은 검증된 롤링 배포 절차를 사용한다.

~~~bash
sudo google_metadata_script_runner startup
sudo tail -n 80 /var/log/mulo-bootstrap.log
sudo docker ps -a
sudo docker logs --tail 100 app
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' --connect-timeout 5 --max-time 15 http://localhost:8000/health
~~~

성공 기준: DB 인증 오류·반복 재시작이 없고 HTTP 200. 공유할 앱 로그에 비밀번호·토큰·연결 문자열이 없는지 확인한다.

## 6. 검증 순서와 성공 기준

### 6-1. VM 자체 — 해당 서비스 VM 안

~~~bash
sudo tail -n 80 /var/log/mulo-bootstrap.log
sudo docker ps -a
sudo docker logs --tail 100 app
~~~

| 서비스 | 확인 주소 | 성공 기준 |
| --- | --- | --- |
| frontend | http://localhost:3000/ | HTTP 200 |
| backend | http://localhost:8080/actuator/health | HTTP 200, 앱 상태 정상 |
| AI | http://localhost:8000/health | HTTP 200, 두 VM 모두 |
| chat | http://localhost:8081/health | 이미지 준비 이후 확인 |

`curl -f`는 오류 HTTP 상태 탐지에 유용하지만 정확히 200인지는 출력 코드로 확인한다.

~~~bash
# 해당 VM의 서비스 포트·경로로 변경
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' --max-time 15 http://localhost:8000/health
curl -fsS --max-time 10 http://localhost:9100/metrics -o /dev/null
~~~

두 번째 명령은 Node Exporter 응답 확인이다. 모니터링 VM의 실제 수집 성공까지 확인해야 수집 설정·방화벽도 검증된다.

### 6-2. 내부 DNS·LB — 앱 VM 안

backend VM에서 AI를, AI VM에서 backend를 호출한다. 아래는 prod이며 staging은 DNS 중 prod를 staging으로 바꾼다.

~~~bash
getent hosts ai.prod.mulo.internal
getent hosts backend.prod.mulo.internal

# backend VM에서
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' --max-time 15 http://ai.prod.mulo.internal:8000/health

# AI VM에서
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' --max-time 15 http://backend.prod.mulo.internal:8080/actuator/health
~~~

성공 기준: DNS가 Terraform의 예약 내부 LB IP로 해석되고 양방향 HTTP 200. 사설 DNS이므로 일반 Mac 인터넷에서 이름이 해석되지 않는 것은 같은 검사 조건이 아니다.

### 6-3. MIG·LB — Mac 터미널

prod AI 예시다. backend·frontend는 이름을 바꾸고, 내부 LB는 backend·AI에만 있다. staging은 접두사를 mulo-v2-staging으로 바꾼다.

~~~bash
gcloud compute instance-groups managed list-instances mulo-v2-ai-mig --project=project-7b071b48-8637-467a-80d --zone=asia-northeast3-a
gcloud compute instance-groups managed describe mulo-v2-ai-mig --project=project-7b071b48-8637-467a-80d --zone=asia-northeast3-a --format='yaml(versions,updatePolicy,targetSize,status)'
gcloud compute backend-services get-health mulo-v2-ai-service --project=project-7b071b48-8637-467a-80d --global
gcloud compute backend-services get-health mulo-v2-ai-internal --project=project-7b071b48-8637-467a-80d --region=asia-northeast3
~~~

성공 기준: 기대 수량·현재 템플릿 일치, VM 작업 완료, 외부·내부 각각 모든 대상 VM이 HEALTHY. 평상시 코드 정책 max_surge_fixed=1·max_unavailable_fixed=0이 live에도 반영됐는지 확인한다. 초기 설치가 오래 걸릴 수 있으며 코드상 autohealing 초기 지연은 600초다.

[get-health 명령](https://docs.cloud.google.com/sdk/gcloud/reference/compute/backend-services/get-health) · [MIG 인스턴스 조회](https://docs.cloud.google.com/sdk/gcloud/reference/compute/instance-groups/managed/list-instances)

이후 실제 도메인에서 frontend와 유효한 backend·AI API를 검사한다. 환경 폴더에서 `terraform output -raw site_url`로 주소를 확인한다. 로컬 /health가 외부에 같은 경로로 노출된다고 가정하지 않는다. URL 맵은 경로를 제거하지 않으므로 /ai/health는 앱이 그 경로를 실제 제공할 때만 사용한다.

### 6-4. 재부팅·VM 교체·CD

아래는 추가로 결과를 확보할 시험이다. staging에서 한 서비스·한 VM씩 진행한다. 현재 기록만으로 완료 처리하지 않는다.

| 시험 | 실행·관찰 방법 | 통과 기준 |
| --- | --- | --- |
| 재부팅 복구 | VM 이름·이미지 기록 → 재부팅 → 부팅 로그·app·HTTP·LB 확인 | 설치 완료 표시가 있어도 앱 실행, HTTP 200·healthy |
| 새 VM 복구 | staging MIG에서 인스턴스 1대 재생성 → 새 VM·로그 확인 | 수동 파일 복사 없이 앱 복구 |
| 내부 주소 유지 | 교체 전후 DNS·LB IP·내부 HTTP 확인 | VM IP가 바뀌어도 같은 서비스 주소로 통신 |
| CD 정상 배포 | workflow_dispatch로 태그 지정 → 템플릿·전체 VM 버전·LB 확인 | 목표 태그로 교체 완료, 실제 외부 기능 정상 |
| 배포 중 가용성 | 별도 터미널에서 주요 API의 시각·HTTP·지연을 반복 기록 | 오류·타임아웃 발생 여부를 근거로 판정 |
| 배포 실패 대응 | 격리한 staging에서 새 템플릿만 실패하도록 구성 | 새 VM 실패 시 배포 대기, 기존 healthy VM·요청 유지 |

수동 CD 검증은 사람이 workflow를 한 번 시작해서 **CI 이미지 → 템플릿 → 새 VM 부팅 → LB 편입 → 이전 VM 종료** 전체 연결을 확인하는 것이다. VM에 SSH로 앱을 수동 설치한다는 뜻이 아니다. prod 전용 workflow만 있다면 prod 인프라 준비 후 검증하고, staging workflow가 있으면 먼저 시험한다.

롤링 정책은 무중단을 위한 설정이지 실제 무중단의 증거는 아니다. 앱 시작·종료 처리와 장시간 요청도 영향을 준다. 운영 시크릿을 삭제했던 사건은 통제된 실패 시험의 증거로 볼 수 없다. 실패 시험에서는 정상 VM도 다시 읽을 공용 시크릿을 삭제하지 말고 새 시험 템플릿만 잘못된 참조를 쓰도록 격리한다.

## 7. 헷갈렸던 지점

- **앱 시작 완료와 정상 응답:** 스크립트는 컨테이너 실행 후 HTTP 200을 기다리지 않는다. 앱 로그·HTTP·LB를 따로 검사한다.
- **plan과 apply:** 2 to add는 아직 생성 전이다. apply 성공 후 시크릿 버전을 넣는다.
- **시크릿 삭제와 값 수정:** 값 수정은 삭제하지 않고 새 버전을 추가한다. 삭제하면 시크릿·IAM 복구가 필요해진다.
- **Mac과 VM 경로:** $HOME/Desktop/ai.env는 Mac에서 실행해야 해당 사용자 바탕화면이다. VM의 root에서는 /root/Desktop이 된다.
- **frontend 빌드 변수와 런타임 env:** 빌드 시 이미지에 들어가는 설정은 CI에서 처리한다. 시크릿 변경만으로 이미 빌드된 프런트 코드가 바뀌지 않는다.
- **최초 전환과 일반 배포:** version ignore를 잠시 풀고 중단 허용 정책을 썼다면 확인 후 일반 정책으로 복구해야 한다. 현재 소스는 일반 정책이며 live는 별도 확인한다.
- **Terraform 템플릿과 현재 MIG 템플릿:** CD 이후 다를 수 있다. live MIG versions를 우선 확인한다. state output은 마지막 갱신 시점 값일 수 있다.
- **staging 중지와 삭제:** mig-power.sh stop은 중지다. resize --size=0은 앱 VM·디스크 삭제이므로 중지 용도로 사용하지 않는다.

staging을 다시 켤 때는 [환경 안내](../environments/staging/README.md#스테이징-전체-중지와-시작)에 따라 Cloud SQL을 먼저 RUNNABLE로 만든 뒤 runtime_enabled=true를 적용하고 mig-power.sh start를 실행한다. 끌 때는 앱을 먼저 멈추고 나머지 런타임을 내린다.

## 10. 기존 MIG·LB 질문 정리

바탕화면 MIG-LB-질문정리.md의 내용을 아래에 통합했다. 구조 설명은 코드 기준이며 실제 검증 상태는 앞의 표를 따른다.

현재 구성은 staging·prod 각각 앱 MIG 4개와 앱 VM 5대입니다. frontend·backend·chat은 각 1대, AI는 2대입니다. Redis·모니터링은 독립 VM이며 오토스케일러는 사용하지 않습니다.

### 외부 LB는 /api와 /ai를 분기하는 L7 용도가 맞나?

맞습니다. HTTPS 외부 LB의 URL 맵이 경로로 서비스를 선택합니다.

| 경로 | 연결되는 서비스 |
| --- | --- |
| `/api`, `/api/*`, `/image`, `/image/*` | backend MIG |
| `/ai/*`, `/internal/tasks/*`(Cloud Tasks 활성화 시) | AI MIG |
| `/ws`, `/ws/*` | chat MIG |
| 나머지 | frontend MIG |

`/ai` 자체는 `/ai/*` 규칙에 포함되지 않아 기본 frontend로 전달됩니다. 이 경로 분기는 내부 LB 추가와 RATE 변경 후에도 그대로입니다. 경로를 선택한 뒤에는 해당 서비스 그룹의 정상 VM으로 요청을 전달합니다.

### 그러면 CPU 사용률은 왜 나왔나?

기존 코드의 외부 LB backend 설정에 `balancing_mode = "UTILIZATION"`이 들어 있었기 때문입니다. 이것은 그룹의 목표 처리 용량을 CPU 사용률 기준으로 판단하는 설정입니다.

`/api`와 `/ai`를 구분하는 기준은 URL 맵입니다. `UTILIZATION`은 그룹의 처리 여유를 판단하는 기준입니다. backend 요청을 CPU가 낮은 AI로 보내거나 자동으로 VM을 늘리는 의미가 아닙니다. 같은 존 안의 개별 VM을 단순히 CPU 사용률 순서로 고른다는 뜻도 아닙니다. [GCP 분산 기준 설명](https://docs.cloud.google.com/load-balancing/docs/backend-service#balancing_mode_target_capacity_and_capacity_scaler)

### 내부 LB는 왜 필요한가?

MIG의 VM이 교체되면 내부 IP가 바뀔 수 있습니다. 따라서 backend env에 AI VM IP를 직접 넣으면 교체 후 통신이 끊길 수 있습니다. AI는 VM도 2대라 호출 주소 하나로 두 VM에 접근할 방법이 필요합니다.

내부 LB가 고정 주소를 유지하고 현재 정상 VM으로 연결합니다. 사설 DNS는 그 고정 IP에 읽기 쉬운 이름을 붙입니다.

```text
backend → ai.prod.mulo.internal:8000 → AI 내부 LB → 정상 AI VM 2대
AI      → backend.prod.mulo.internal:8080 → backend 내부 LB → 정상 backend VM
```

VM이 교체돼도 env의 서비스 주소를 바꿀 필요가 없습니다. staging은 DNS 이름의 `prod` 대신 `staging`을 사용합니다.

### 내부 LB를 만들면서 외부 LB를 왜 RATE로 바꾸나?

외부 HTTP LB와 내부 TCP LB가 **동일한 backend·AI MIG를 공유**하기 때문입니다. 내부 TCP LB는 `CONNECTION` 분산 설정을 사용합니다. GCP는 같은 그룹에 여러 LB를 연결할 때 호환되는 분산 설정을 요구합니다.

`UTILIZATION`은 다른 방식과 공유할 수 없고, 외부의 `RATE`와 내부의 `CONNECTION`은 함께 사용할 수 있습니다. 이 제약에 맞춰 backend·AI의 외부 설정만 RATE로 변경합니다. frontend·chat의 설정과 URL 맵은 유지합니다. [GCP의 그룹 공유 제약](https://docs.cloud.google.com/load-balancing/docs/backend-service#restrictions_and_guidance_for_instance_groups)

### RATE는 무엇을 기준으로 하나? 왜 30 RPS인가?

RATE는 초당 새 HTTP 요청 수로 목표 처리 용량을 표현합니다. 현재 선택한 값은 **VM당 30 RPS**입니다. 성능 측정으로 확정한 값은 아니며 사용자가 이번 구성의 기준값으로 지정한 값입니다.

| 서비스 | VM 수 | VM당 기준 | 정상 상태의 합계 목표 용량 |
| --- | --- | --- | --- |
| backend | 1대 | 30 RPS | 30 RPS |
| AI | 2대 | 30 RPS | 60 RPS |

롤링 배포의 임시 추가 VM이나 장애로 정상 VM 수가 달라지면 목표 합계도 달라집니다. 서비스별 값은 `service_max_rate_per_instance`로 조정합니다.

```hcl
service_max_rate_per_instance = {
  backend = 30
  ai      = 30
}
```

실제 처리량은 요청 종류·응답 시간·오류율을 부하 테스트로 확인해 정합니다. AI 작업처럼 오래 걸리는 요청은 RPS와 동시 처리 수가 서로 다르므로 함께 확인해야 합니다.

### 30 RPS를 넘으면 차단되거나 VM이 늘어나나?

이 값은 요청 차단 한도가 아닙니다. 자동으로 429를 반환하지 않으며 오토스케일러도 추가하지 않습니다.

현재는 서비스마다 서울 `asia-northeast3-a` 존의 MIG 하나를 사용합니다. 다른 그룹으로 우회할 곳이 없으므로 목표 용량을 넘어도 해당 그룹으로 요청이 계속 전달될 수 있습니다. 실제 처리량 제한이 필요하면 앱·프록시에서 별도 제한을 구현해야 합니다. [GCP 목표 용량과 초과 요청 처리](https://docs.cloud.google.com/load-balancing/docs/backend-service#balancing_mode_target_capacity_and_capacity_scaler)

### backend와 AI 환경변수는 어떤 주소를 쓰나?

같은 Compose의 `http://ai:8000`, `http://backend:8080/` 대신 환경별 사설 DNS를 사용합니다.

| 환경 | backend의 `AI_BASE_URL` | AI의 `BACKEND_INTERNAL_URL` |
| --- | --- | --- |
| staging | `http://ai.staging.mulo.internal:8000` | `http://backend.staging.mulo.internal:8080/` |
| prod | `http://ai.prod.mulo.internal:8000` | `http://backend.prod.mulo.internal:8080/` |

기본값 기준입니다. `terraform output ai_base_url`, `terraform output backend_internal_url`로 확인하고 Secret Manager의 해당 서비스 env에 등록합니다. URL 끝의 `/`는 앱이 요구하는 형식에 맞춥니다. 내부 LB는 경로를 그대로 전달합니다.

### MIG 재생성 때 Compose 파일과 IP는 어떻게 되나?

VM 안에서 직접 만든 Compose·env·데이터는 인스턴스 템플릿에 저장되지 않습니다. 현재 앱 부팅 디스크는 VM 교체 때 삭제되므로 그 파일도 사라집니다. 일반 중지·시작은 같은 VM·디스크·내부 IP를 유지하지만 교체는 새 VM·새 디스크가 됩니다.

이번 앱 구성은 Compose 대신 부팅 스크립트의 `docker run`을 사용합니다. 새 VM은 Artifact Registry에서 이미지를 받고 Secret Manager에서 env를 읽어 `app`과 `node-exporter`를 실행합니다. Redis·모니터링의 수동 Compose 설치는 유지합니다.

### 오토힐링은 어떤 템플릿으로 복구하나?

MIG가 현재 연결한 템플릿을 기준으로 복구합니다. CD 배포가 끝났으면 CD가 만든 템플릿의 이미지 태그·부팅 설정이 기준입니다. VM 안에서 수동으로 바꾼 설정을 자동 저장해 복구하지는 않습니다.

`instance_template_names`는 Terraform 기반 템플릿의 이름입니다. 실제 현재 연결은 MIG의 `versions` 또는 `mig_instance_template_urls`로 확인합니다. CD 이후 Terraform 출력은 refresh를 포함한 plan/apply로 갱신해야 합니다.

### Terraform과 CD가 서로 템플릿을 덮어쓰지 않나?

최초 전환은 Terraform이 새 부팅 템플릿을 MIG에 연결합니다. 이후에는 `ignore_changes = [version]`을 사용해 CD가 연결한 템플릿을 유지합니다. staging은 전원 스크립트가 바꾼 실행·중지 수량도 유지합니다.

부팅 스크립트나 VM 사양을 나중에 바꾸려면 현재 배포 태그를 Terraform 입력에 맞춘 뒤 version 무시를 잠시 해제해 새 템플릿을 연결하고 다시 원래 설정으로 복구합니다. 별도 CD 모드나 전환 도구는 사용하지 않습니다. 적용 순서는 [앱 자동 부팅 안내](../environments/BOOTSTRAP.md)에 있습니다.

### 전달한 CD 예시는 그대로 사용할 수 있나?

메타데이터로 태그를 전달하고 새 템플릿으로 롤링 배포하는 방향은 현재 IaC와 맞습니다. 다음 항목은 수정해야 합니다.

- 운영 backend MIG 이름은 `mulo-v2-backend-mig`입니다. 예시의 `muro-backend-mig`와 다릅니다.
- `instance-templates create --source-instance-template`는 지원하지 않는 옵션이므로 CD 담당자가 지원되는 복사 방식으로 수정해야 합니다. IaC에는 CD 템플릿 복사 도구를 추가하지 않습니다.
- 승인·배포 대기 후 현재 템플릿을 다시 조회하고, 해당 CI 이미지 태그와 환경별 고유 템플릿 이름을 사용합니다.
- 모든 VM의 버전 전환 완료와 실제 LB의 healthy 상태를 함께 확인합니다.

IaC와 CD가 공유하는 메타데이터와 최초 연결 순서는 [앱 부팅 안내](../environments/BOOTSTRAP.md)를 참고하세요.
