# Mulo 모니터링 구축·검증 실행 계획

작성: 2026-10-15 (KST). 운영 IaC 테스트·검증을 완료했다는 사용자 보고 이후의 작업 계획이다.
이 문서는 설계·실행 안내이며 모니터링 구축 완료 보고가 아니다. 실제 실행 결과는 마지막 기록표에 남긴다.

## 1. 오늘 목표와 완료 기준

**장애 발생 → 탐지·알림 → 대시보드·로그로 원인 확인 → 복구 확인**을 한 번 실제로 검증한다.

오늘의 작업 문장:

> MIG 교체에도 유지되는 지표·로그 수집을 구성하고, 서비스 상태 대시보드 1개·핵심 알림 3개·런북 1개를 만든다. staging 장애 재현으로 탐지부터 복구 확인까지 검증한다.

완료 기준:

- [ ] 앱 VM 교체 후 새 VM 지표가 수동 IP 수정 없이 수집된다.
- [ ] 새 VM 앱 로그도 별도 수동 설치 없이 Loki에서 조회된다.
- [ ] 대시보드에서 서비스 상태 → 인스턴스 → 자원 → 로그 순서로 조사할 수 있다.
- [ ] 알림 3개를 설정하고, 시험 가능한 조건의 실제 발송·수신·해제를 확인한다.
- [ ] staging에서 AI 한 대의 장애·복구를 재현하고 시각과 결과를 기록한다.
- [ ] 알림에서 런북으로 이동해 조사·복구 절차를 따라갈 수 있다.
- [ ] 수집 설정·알림 규칙·대시보드를 재현 가능한 파일로 보관한다.

시간이 부족하면 HTTP 프로브와 VM 지표를 먼저 연결한다. 앱 요청량·지연 지표는 실제 노출 여부를 확인한 후 추가하고, 미구현 패널은 완료로 표시하지 않는다.

## 3. 먼저 MIG 교체에도 수집이 이어지게 한다

### 지표

Prometheus의 GCE Service Discovery로 VM을 자동 탐색한다. 대상 환경과 서비스로 필터링하고 GCE 라벨을 조회용 라벨로 연결한다. Prometheus 실행 계정의 VM 조회 권한을 준비한다.

- VM별 CPU·메모리·디스크는 각 VM의 Node Exporter에서 수집한다.
- 앱 지표도 각 VM의 실제 metrics 경로에서 수집한다.
- AI 내부 LB 주소는 서비스 접속 성공 여부를 검사하는 프로브 대상으로 사용한다.
- VM별 지표를 LB 주소 하나로 수집하면 두 AI 인스턴스의 상태를 안정적으로 구분하기 어렵다.
- VM 교체 시 이전 대상 제거와 새 대상 수집을 함께 확인한다.
- 발견된 대상만으로 기대 수량을 정하지 않는다. 대상 전체가 사라지면 up=0 시계열조차 남지 않을 수 있으므로 No Data·대상 부재를 별도로 다룬다.

권장 조회 차원은 environment·service·instance다. service로 모아서 보고 instance로 내려가 조사할 수 있게 구성한다.

검증: staging VM 교체 전후의 이름·IP·Prometheus Targets를 기록하고 새 VM 수집까지 걸린 시간을 측정한다.

[Prometheus GCE Service Discovery](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#gce_sd_config)

### 로그

VM의 Docker stdout/stderr와 필요 시 부팅 로그를 수집할 경로를 정한다. 새 MIG VM에도 수집기가 자동으로 설치·실행되도록 구성해야 한다. 현재 앱 bootstrap.sh가 Loki 로그 수집기까지 설치한다고 가정하지 않는다.

- environment·service를 기본 구분값으로 사용한다.
- VM 식별 정보로 특정 인스턴스의 로그를 찾을 수 있게 한다.
- request_id·사용자 ID·원문 URL처럼 값의 종류가 매우 많은 정보는 Loki 인덱스 라벨보다 로그 필드·구조화 메타데이터로 다루는 것을 우선 검토한다.
- 인증 정보·env 원문은 수집 로그에 출력하지 않는다.
- 앱 로그와 /var/log/mulo-bootstrap.log는 역할이 다르므로 서비스 시작 실패도 조회할 수 있게 한다.

검증: 시험 요청 또는 구분 가능한 시험 로그를 만들고 Loki에서 환경·서비스·시각으로 찾는다. VM 교체 후에도 반복한다.

[Loki 라벨 설계 원칙](https://grafana.com/docs/loki/latest/get-started/labels/bp-labels/)

## 4. 대시보드 1개를 조사 순서로 구성한다

상단에서 사용자 영향, 아래에서 원인을 확인한다. 공통 선택 필터는 환경·서비스·인스턴스로 둔다.

| 순서 | 답해야 할 질문 | 패널 | 수집 방식·주의 |
| --- | --- | --- | --- |
| 1 | 사용자가 이용할 수 있나? | 주요 URL 성공 여부·응답 시간 | HTTP 프로브. 정상 기대 상태·응답을 명시 |
| 2 | 어느 서비스가 문제인가? | 요청량·오류율·p95 지연 | 앱 또는 LB 지표. 같은 요청을 중복 집계하지 않음 |
| 3 | 두 AI 중 한 대만 문제인가? | VM별 앱 헬스·수집 상태·기대/정상 수량 | VM별 프로브와 수집 상태를 구분 |
| 4 | 자원이 부족한가? | CPU·메모리·디스크·스왑 | Node Exporter. VM별 비교 |
| 5 | 변경 직후 시작됐나? | 배포 시각·버전·오류 로그 | 배포 주석·같은 시간대 Loki 링크 |

지표 해석:

- Node Exporter의 up=1은 해당 exporter 수집 성공이다. 앱 정상 응답이나 DB 연결 성공과 같지 않다.
- health 프로브 성공은 그 경로의 응답 성공이다. 실제 게시물 조회 등 주요 기능 성공과 구분한다.
- p95는 관측 요청의 약 95%가 그 시간 이내라는 뜻이다. 히스토그램 등 실제 수집 가능한 지표가 필요하며 평균만으로 대체하지 않는다.
- 요청이 없거나 표본이 적으면 오류율·p95를 과도하게 해석하지 않는다. 저트래픽 시간은 프로브를 함께 본다.
- /ai/health가 외부에서 유효한지는 앱 경로를 확인한다. 외부 URL 맵은 /ai 접두사를 자동 제거하지 않는다.
- 모니터링 VM에서 외부 도메인을 검사하면 해당 위치에서의 접근성을 확인한다. 인터넷 사용자 관점의 장애까지 보려면 추후 독립된 외부 관측점을 추가한다.

초기 HTTP 프로브 도구로 Blackbox Exporter를 사용할 수 있다. 내부 LB 프로브와 개별 VM 프로브의 목적을 구분해 설정한다.

[Google SRE 모니터링 원칙](https://sre.google/sre-book/monitoring-distributed-systems/) · [Blackbox Exporter](https://github.com/prometheus/blackbox_exporter)

## 5. 핵심 알림 3개

다음은 초기 제안값이며 확정된 운영 기준이 아니다. 실제 응답 특성·수집 간격·배포 시간을 보고 조정한다. 기존 Grafana Alerting 또는 기존 알림 경로 하나로 시작한다.

| 알림 | 초기 조건 예시 | 심각도·대응 |
| --- | --- | --- |
| 주요 서비스 응답 실패 | 주요 URL 프로브가 2분간 연속 실패 | 긴급. LB → 앱 헬스 → 로그 |
| AI 가용 인스턴스 감소 | 정상 AI가 기대 수량 2대 미만인 상태가 설정 시간 지속 | 1대면 경고, 전체 실패는 더 높은 심각도. 배포·VM 조사 |
| 모니터링 디스크 여유 부족 | 데이터 볼륨 여유 15% 미만이 10분 지속 | 경고. Prometheus·Loki 사용량·보존 정책 |

알림 설계 시 결정할 것:

- No Data·평가 오류·대상 전체 소실 시 어떻게 알릴지 정한다.
- AI 정상 수량은 exporter up 개수로 대신하지 않는다. VM별 앱 프로브 또는 LB health 등 선택한 근거를 명시한다.
- 롤링 배포의 짧은 전환 상태와 지속 장애를 구분한다. 유지보수 예외는 종료 시간을 정하고 전체 서비스 실패까지 가리지 않는다.
- 보낸다는 설정만으로 끝내지 않는다. 실제 수신·중복 여부·복구 알림을 확인한다.
- 모니터링 VM 자체가 멈추면 같은 VM의 알림도 멈출 수 있다. 추후 외부 감시 대상으로 등록한다.

알림 메시지에 포함할 정보:

> 환경 / 서비스 / 대상 / 발생 시각 / 현재 값·조건 / 대시보드 링크 / 런북 링크

[Prometheus 알림 원칙](https://prometheus.io/docs/practices/alerting/)

## 6. staging 장애 재현으로 검증한다

### 시험 A: AI 한 대의 앱 장애

운영이 아닌 staging에서 한 대만 대상으로 한다. 시험 전에 대상·정상 상태·복구 방법을 정하고 기존 요청에 미치는 영향을 확인한다.

1. AI 두 대의 정상 앱 헬스·LB 상태와 모니터링 수집을 기록한다.
2. 한 대의 app 컨테이너를 잠시 중지하는 방식으로 장애를 만든다.
3. VM·Node Exporter 지표는 남고 앱 프로브가 실패하는지 관찰한다.
4. AI 가용 수량 경고가 기대한 조건으로 발생하는지 확인한다.
5. 같은 시간대 로그와 VM 상태로 조사 경로를 따라간다.
6. 앱을 복구하거나 MIG 자동 복구를 관찰하고 HTTP·LB·알림 해제를 확인한다.

MIG가 먼저 복구하거나 시험이 짧아서 알림 지속 조건을 채우지 못할 수 있다. 알림 발생을 기다린 실제 시간과 복구 주체를 기록하고 결과를 임의로 성공 처리하지 않는다. 코드의 autohealing 초기 지연 600초는 새 VM 초기 부팅 시 유예이며 모든 장애에 대한 고정 복구 시간이 아니다.

### 시험 B: VM 교체 후 수집 복구

staging MIG에서 한 VM을 재생성하고, 새 VM의 앱·Node Exporter·로그 수집이 자동으로 복구되는지 확인한다. 시험 A는 앱 장애 탐지, 시험 B는 수집의 자동 복구를 검증한다.

관찰 항목:

- 이전 VM 제거 및 새 VM 이름·IP
- Prometheus 자동 탐색·수집 시작
- 새 VM의 Loki 로그 도착
- 내부 LB·개별 앱 헬스
- 이전 VM 관련 알림이 계속 남는지
- 새 VM 부팅 실패를 정상 배포 대기와 구분할 수 있는지

전체 서비스 응답 실패 알림은 AI 한 대 중지만으로 발생하지 않을 수 있다. 별도의 staging 시험용 프로브 대상을 실패시키는 등 통제된 방법으로 그 규칙의 실제 알림 경로를 검증한다. 디스크 경고도 시험 규칙·평가 테스트로 확인하며 실제 디스크를 채우는 방식은 필요하지 않다.

## 7. 최소 런북: AI 가용 인스턴스 감소

| 단계 | 확인·조치 |
| --- | --- |
| 사용자 영향 | 주요 기능·내부 LB 응답 확인. 한 대 감소와 전체 실패 구분 |
| 최근 변경 | 배포·MIG 교체·시크릿 변경 시각 확인 |
| 범위 확인 | 어떤 VM의 앱 프로브가 실패했는지, Node Exporter 수집도 실패했는지 비교 |
| 앱 조사 | docker ps -a, docker logs --tail 100 app |
| 부팅 조사 | /var/log/mulo-bootstrap.log에서 env·이미지·실행 실패 확인 |
| 의존성 | DB 인증·연결, backend↔AI 통신, DNS·LB 상태 확인 |
| 복구 | 원인에 따라 설정 수정 후 재배포·재기동 또는 검증된 이전 배포로 복구 |
| 종료 판단 | 기대 수량의 앱·LB 정상, 주요 요청 성공, 알림 해제 확인 |

예전에 관찰한 PostgreSQL mulo 인증 실패처럼 컨테이너 생성 이후에 앱이 실패할 수 있다. “앱 시작 완료” 로그만으로 복구 완료 처리하지 않는다. 복구 작업으로 해당 VM의 app이 재시작될 수 있으므로 한 대씩 결과를 확인한다.

탐지 시간은 장애 발생부터 알림 수신까지, 복구 시간은 이 시험에서 정한 시작점부터 서비스 정상 확인까지 계산한다. 단일 시험 결과를 평균 탐지·복구 시간이라고 쓰지 않는다.

## 8. 오늘 실행 순서·결과

시간 배분은 제안이며 현재 스택 준비 상태에 따라 조정한다.

| 순서 | 작업 | 예상 배분 | 실제 결과·증거 |
| --- | --- | --- | --- |
| 1 | 현재 스택·권한·지표·로그 경로 조사 | 30분 | |
| 2 | 자동 탐색·로그 수집·HTTP 프로브 연결 | 90분 | |
| 3 | 대시보드 1개 구성 | 60분 | |
| 4 | 알림 3개·런북 1개 | 60분 | |
| 5 | staging 앱 장애·VM 교체 시험 | 90분 | |
| 6 | 결과 정리·설정 파일 보관 | 30분 | |

보관 대상은 Prometheus 수집·규칙 설정, 로그 수집기 설정, Grafana 대시보드 JSON·provisioning 설정, 런북·시험 결과다. 실제 비밀번호·토큰·알림 webhook은 저장소에 넣지 않는다.

완료 보고 예시:

> GCE 자동 탐색으로 MIG 교체 후 수집 대상이 자동 갱신되도록 구성했다. staging AI 한 대의 장애를 재현해 N초 후 알림 수신을 확인했고, 대시보드·로그를 통해 원인을 확인한 뒤 M분 만에 복구했다.

N·M은 시험 결과로 채운다. 미완료 작업은 별도 남긴다.

## 9. 이후 깊이를 더할 지표

오늘의 탐지·복구 흐름이 완성된 뒤 실제 병목에 맞춰 추가한다.

| 관점 | 추가 지표·실험 |
| --- | --- |
| backend → AI | 호출 성공률·타임아웃·재시도·p95 지연, 서비스 간 request_id 연결 |
| AI 비동기 작업 | 대기 작업 수·가장 오래 대기한 시간·처리 성공률·재시도 |
| DB | 연결 풀 대기·사용량·쿼리 지연·인증 실패 |
| 사용자 기능 | 위치 기반 조회 등 실제 주요 기능의 성공률·지연 기준 |
| 배포 영향 | 배포 주석과 오류율·지연 변화 비교 |
| 운영 비용 | 지표 시계열 수·로그 유입량·보존 기간·디스크 증가량 |
| 모니터링 가용성 | 모니터링 VM 외부 감시·데이터 영속성·재부팅 복구 |

SLO는 사용자 기능과 측정 범위·기간을 정한 뒤 합의한다. 아직 측정하지 않은 가용성·성능 향상 수치를 성과로 쓰지 않는다.

## 10. Compose 파일 없이 앱 컨테이너가 뜨는 원리

### 시작 계기는 SSH 접속이 아니라 VM 부팅

현재 staging·prod 앱 VM은 인스턴스 템플릿에 등록된 startup-script로 앱을 실행한다. GCE 게스트 환경이 부팅 과정에서 이 스크립트를 root로 실행하므로 로그인하거나 Compose 파일을 만들 필요가 없다.

~~~text
Terraform 환경 main.tf
  → bootstrap.sh 파일을 읽어 모듈에 전달
  → 인스턴스 템플릿에 startup-script와 앱 메타데이터 등록
  → MIG가 현재 연결된 템플릿으로 VM 생성
  → VM 부팅 시 GCE가 startup-script 실행
  → env 다운로드 + 이미지 pull
  → docker run으로 app 실행
  → node-exporter 실행
~~~

코드 연결:

- [환경 main.tf](../environments/prod/main.tf): bootstrap_script에 bootstrap.sh 내용 전달
- [모듈 compute.tf](../modules/prod_modules/compute.tf): metadata_startup_script와 앱 메타데이터 설정
- [bootstrap.sh](../environments/prod/bootstrap.sh): 메타데이터 조회·env·이미지 준비·docker run

CD 이후에는 MIG가 현재 연결한 템플릿의 스크립트·메타데이터가 기준이다. 로컬 Terraform 파일을 고치기만 해서 실행 중 VM의 설정이 바뀌지는 않는다.

### 무엇을 실행하고 포트는 어떻게 정하나?

| 입력 | 위치 | AI 기본 예시 |
| --- | --- | --- |
| 이미지 경로 | app-image 메타데이터 | asia-northeast3-docker.pkg.dev/project-7b071b48-8637-467a-80d/ai/ai |
| 이미지 태그 | app-image-tag 메타데이터 | 최초 1.5.0, 이후 CD 태그 |
| 시크릿 이름 | app-env-secret 메타데이터 | mulo-v2-ai-env |
| 포트 | app-port 메타데이터 | 8000 |
| env 원문 | Secret Manager | VM에서 /opt/app/app.env로 저장 |
| 컨테이너 안의 앱 시작 명령 | Docker 이미지의 ENTRYPOINT·CMD | 이미지에 정의된 명령 |

실제 스크립트의 실행 명령:

~~~bash
docker run -d --name app --restart unless-stopped \
  --env-file /opt/app/app.env -p "$PORT:$PORT" --stop-timeout 60 "$IMAGE:$TAG"
~~~

이 코드는 bootstrap.sh 안에서 변수가 채워진 뒤 실행된다. 빈 변수 상태의 터미널에 그대로 복사해 실행하는 용도가 아니다.

AI에서 PORT=8000이면 -p 8000:8000으로 실행한다. 왼쪽은 VM의 포트, 오른쪽은 컨테이너의 포트다. 앱 프로세스도 컨테이너 안에서 그 포트에 접근 가능하게 리슨해야 하며, Docker가 앱의 리슨 포트를 자동으로 바꾸는 것은 아니다. 현재 스크립트는 별도 앱 명령을 넘기지 않으므로 이미지의 기본 ENTRYPOINT·CMD를 사용한다.

컨테이너 이름은 서비스별로 달라도 되는 개념이지만 이 스크립트는 각 VM에 app이라는 고정 이름을 쓴다. frontend VM의 app과 AI VM의 app은 서로 다른 VM에 있는 별도 컨테이너다.

### Compose 항목과 현재 설정의 대응

| Compose에서 지정하던 것 | 현재 앱 실행에서 지정하는 곳 |
| --- | --- |
| image | app-image + app-image-tag |
| env_file | Secret Manager → /opt/app/app.env → --env-file |
| ports | app-port → -p VM포트:컨테이너포트 |
| restart | --restart unless-stopped |
| container_name | --name app |
| command·entrypoint | 현재는 이미지 기본값 |
| 같은 VM의 서비스 이름으로 통신 | 서비스별 VM·내부 LB·사설 DNS |

Docker Compose는 Docker 컨테이너를 실행하는 한 가지 방식이다. 현재 앱 VM의 실행 설정은 템플릿 메타데이터와 부팅 스크립트에 들어 있다. Redis·모니터링 독립 VM은 별도 Compose를 사용할 수 있다.

### 재부팅과 VM 교체

- 최초 부팅에는 Docker·gcloud·Ops Agent·스왑을 설치하고 설치 완료 파일을 만든다.
- 같은 VM 재부팅에는 최초 설치를 건너뛰지만 앱 실행 부분은 다시 수행한다.
- 새 VM으로 교체하면 새 디스크에서 설치·env 다운로드·이미지 pull을 다시 수행한다.
- --restart unless-stopped는 기존 컨테이너의 Docker 재시작 정책이다. 새 VM에서 이미지를 받아 컨테이너를 만드는 작업은 startup-script가 담당한다.
- 현재 스크립트는 env·이미지 준비 후 기존 app을 종료·제거하고 새로 실행한다.
- chat처럼 app-image가 없으면 앱 기동을 건너뛴다.

### VM 안에서 실제 설정 확인

아래는 조회 명령이다. env 값은 출력하지 않는다.

~~~bash
sudo docker ps
sudo docker port app
sudo docker inspect --format '{{.Config.Image}}' app
sudo docker inspect --format '{{json .Config.Entrypoint}} {{json .Config.Cmd}}' app
sudo tail -n 80 /var/log/mulo-bootstrap.log
sudo journalctl -u google-startup-scripts.service --no-pager -n 80
~~~

실행 중 컨테이너 설정과 앱 로그를 확인해야 실제 동작을 알 수 있다. 이미지·스크립트가 다르면 동작도 달라질 수 있다.
